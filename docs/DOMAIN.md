# 业务模型与报表口径

状态：目标业务规范；历史退款、币种和期初范围仍待校准。本系统提供个人管理报表，不声称已有数据构成完整法定财务报表。

## 1. 现有复式记账模型

`account` 是会计科目，包含资产、负债、净资产、收入、支出五类，不能把所有科目都显示为银行账户。`transaction` 是交易头，`entry` 是借/贷分录，单笔交易可以有多条分录。支付渠道另存于交易头。

记账单位是交易及其全部分录。已入账要求：至少两条有效分录、每条金额为正、科目有效且属于同一账本、借方总额等于贷方总额、时间与币种有效、付款状态和会计含义已确认。零分录虽然算术差额为零，也不满足入账条件。

金额数据库沿用 `numeric(12,2)`；API 金额为十进制字符串。输入不能隐式四舍五入超过两位的小数，也不得通过负金额表示反向分录；反向操作交换借贷方向。

## 2. 交易状态、入账状态与完整性

保留原 `status`：`success/pending/cancel/refund/partial_refund`。新增独立入账状态拟为 `draft/posted/reversed`，来源状态不因补录而改写。完整性与待核对原因由规则计算。

| 情况 | 处理 |
| --- | --- |
| 成功但无分录、金额未知或科目缺失 | 草稿/待补录，不进入正式报表 |
| 信息完整但含义尚未确认 | 待核对，不自动发布到正式报表 |
| pending / cancel | 保留来源信息，首期不计正式报表 |
| success 且验证完成 | 可正式入账 |
| refund / partial_refund | 先确认是退款事件还是原消费状态；按关联和实际分录入账 |
| 商户/备注为空 | 视交易类型提供提醒；内部转账等不强制填写商户，不阻塞所有入账 |

来源“成功”不能直接映射成“已入账”。旧数据在迁移中保留原状，先生成候选映射与核对清单，再确认可入账集合。

## 3. 资产负债

设某科目截止时点的借方累计为 D、贷方累计为 C。资产余额 = D − C，负债余额 = C − D；均基于同一已入账集合、账本、币种和截止时点。

- 总资产 = 资产科目余额合计；总负债 = 负债科目余额合计；净资产 = 总资产 − 总负债。
- 以有符号余额保留贷方资产/借方负债等异常或抵减，不取绝对值美化；必要时提示待核对。
- 未结转模式下，累计净资产应可由「净资产科目余额 + 累计收入净额 − 累计支出净额」解释。结转分录必须有专门类型和期间策略，不能再把已经结转的损益加一次。
- 首期建议不自动做年末结转。期初通过平衡的 opening 交易记入，不能同时把余额种子和历史分录重复相加。
- 资产负债是时点数，起始日期不裁剪历史；截止日前的缺项会影响余额。没有完整期初/覆盖历史时标记「已记录范围余额」，不能宣称实际全部资产。
- 默认账面价值；投资市值、应计收益或折旧仅在明确记录的估值/调整分录中反映。

## 4. 损益

期间收入 = 收入科目贷方 − 借方；期间支出 = 支出科目借方 − 贷方；期间净收益 = 收入 − 支出。按 Asia/Shanghai 本地起始日零点到结束日次日零点构成半开区间，数据库存储 timestamptz。

损益依据实际记录的经济事项，不等同现金收付：信用卡消费影响支出，信用卡还款不重复计支出；购置投资资产不直接等于费用；借款本金到账不记收入。缺少应计事项时标记已记录损益范围，不据此声称完全权责发生制。

## 5. 现金流量

现金科目通过显式 `is_cash_equivalent` 配置；先核实活期存款、现金、支付钱包等，信用卡负债不属于现金，不能按科目名称猜测。

每笔已入账交易在现金范围内计算：`现金净变化 = Σ现金借方 − Σ现金贷方`。只有现金科目之间互转的交易，现金净变化为零，从对外流入/流出排除并单独呈现转账记录。

多分录复合交易不能仅按交易净额推导“流入/流出”：同时含现金收支时，会掩盖真实毛额。拟增加现金流分配记录，按实际流入/流出及生活、投资、筹资用途拆分；分配净额必须等于现金净变化。简单交易可从模板生成，含手续费/多方流向的交易需要明确拆分。

现金净增加 = 对外流入 − 对外流出；同口径期末现金 − 期初现金 = 现金净增加 + 单独列示的非现金调整影响。opening 作为期初衔接，不计期间经营/投资/筹资现金流。存在调整未分类时，展示桥接差额，不能强行归到生活支出。

首期 CNY 假设成立时不引入汇兑。发现混合币种必须阻止跨币种直接汇总，在数据迁移前补币种与汇率口径。

## 6. 退款与冲销

历史退款字段只有状态和分录，尚未核实其编码方式。不能把所有 refund 排除，也不能认为 refund 都是新退款事件并自动翻转金额。

目标规则：原消费保留；退款用独立交易关联 `refund_of_transaction_id`，按实际退款日期入账，支持多次部分退款；累计退款不超过可退原金额，特殊调整走明确类型。需在并发事务里锁定原交易并核对累计额度。

例：银行消费 100，随后退回 30，原消费「借支出 100 / 贷银行 100」，退款「借银行 30 / 贷支出 30」，累计净支出 70。信用卡退款通常减少负债，尚未回到现金账户时不计现金流入。

取消未入账交易不产生分录。撤销已入账交易用反向冲销记录：原交易分录仍属于历史已发生记录，冲销分录在冲销日计入，两者合计抵销；`reversed` 是关系/展示状态，不能把原分录排除后又计入反向分录。

## 7. 三表核对示例

以下为独立虚构例子，假设余额足够、无税费。

| 事项 | 分录 | 资产变化 | 负债变化 | 净资产变化 | 现金净变化 | 净收益 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 工资 10,000 | 借银行 / 贷收入 | +10,000 | 0 | +10,000 | +10,000 | +10,000 |
| 银行消费 100 | 借支出 / 贷银行 | −100 | 0 | −100 | −100 | −100 |
| 信用卡消费 100 | 借支出 / 贷信用卡负债 | 0 | +100 | −100 | 0 | −100 |
| 信用卡还款 100 | 借信用卡负债 / 贷银行 | −100 | −100 | 0 | −100 | 0 |
| 银行转入钱包 100 | 借钱包 / 贷银行 | 0 | 0 | 0 | 0 | 0 |
| 借款到账 1,000 | 借银行 / 贷借款负债 | +1,000 | +1,000 | 0 | +1,000 | 0 |
| 买入投资资产 500 | 借投资资产 / 贷银行 | 0 | 0 | 0 | −500 | 0 |
| 银行收到退款 30 | 借银行 / 贷原支出科目 | +30 | 0 | +30 | +30 | +30 |

这些用例应成为 SQL 与 UI 验收的共同基准。报表先验证分子、分母、期间、纳入集合和排除项，再讨论展示。
