# 报表口径

人民币，Asia/Shanghai。仅基于现有三表，不增加管理字段。

## 完整性

有至少两条正金额分录、科目齐全、借贷平衡才是完整交易。来源状态为 success、refund、partial_refund 的完整交易计入损益及现金流；pending、cancel 不计入。缺分录/缺科目的记录留在待补录队列。零分录不能当作零金额的完整交易。

目前完整成功交易 406 笔，完整退款 33 笔，合计 439 笔进入报表。现有退款分录主要为借资产/负债、贷支出，按照方向冲减支出，不能一概排除。历史记录不自动合并或改状态。

## 资产负债与损益

- 资产余额：累计借方 − 贷方。
- 负债余额：累计贷方 − 借方。
- 净资产：资产 − 负债。
- 期间收入：收入科目贷方 − 借方。
- 期间支出：支出科目借方 − 贷方。
- 净收益：收入 − 支出。

当前资产负债使用用户的 balance 物化视图：只排除同笔包含未匹配科目的分录，不额外筛选状态或完整性。balance_history 同口径计算北京时间每日累计余额，覆盖最早有效交易至维护当天，无交易日承接前日。当前 balance 含全部已录入日期；历史快照只累计到所选日末。损益使用北京时间期间半开区间。保留有符号余额，不用绝对值修饰报表。历史仅覆盖已记录范围，不能宣称全部资产余额；没有另存期初余额或自动结转机制。

## 现金流自动计算

现金范围为资产类型下的“现金及等价物”子类（现有 7 个科目）。每笔完整交易计算现金借方 − 贷方：正值为流入，负值为流出，零值不增加收支。

同笔现金账户之间转账自动抵销。退款在同笔交易中冲减原现金支出。现金流分类先判断收入/支出科目（生活），再判断非现金资产（投资），剩余为筹资；可从流水查看全部分录。

该口径是个人管理用的逐笔净现金流，不额外保存毛流量分配。在相同完整交易集合内，期末现金 − 期初现金 = 同期间净现金流。用户的新 balance 纳入范围更宽，因此不强制其现金余额变化与现金流报表相等。

首页“未来30天”使用从首页数据快照时点起的30天半开区间，仅汇总已录入且符合上述完整性及成功/退款状态的未来日期交易；pending 状态不计入。这是已记录范围汇总，不是历史外推预测。现金流默认所选月份，图表与明细改为北京时间逐日统计，合计与分组均从用户的 `financial.cashflow` 经 `cashflow_read` 筛选，由 Data API 在 PostgreSQL 中进行 numeric 聚合。月度现金流截至所选月末或数据快照时点，以较早者为准。

## 同笔退款

例：消费 100 后退回 30，同一 transaction 下保留“借支出100 / 贷银行100”，追加“借银行30 / 贷支出30”；卡片净支出70、现金净流出70。再次退款继续追加同一交易的分录。

现有模型只有交易头的一个 occurred_at，所以同笔退款随该交易日期归期。若未来需要按不同退款发生日分期展示，另行明确数据模型需求；本轮不添加字段或事件表。

## 验证样例

| 事项 | 净资产变化 | 现金变化 | 净收益 |
| --- | ---: | ---: | ---: |
| 工资 10000 | +10000 | +10000 | +10000 |
| 银行消费100、同笔退款30 | −70 | −70 | −70 |
| 信用卡消费100 | −100 | 0 | −100 |
| 信用卡还款100 | 0 | −100 | 0 |
| 银行转钱包100 | 0 | 0 | 0 |
| 借款到账1000 | 0 | +1000 | 0 |
| 购买投资500 | 0 | −500 | 0 |

以上为虚构测试数据。合计净收益9830、现金净增加10330，已在 SQL 测试中验证。

首页首屏使用 `financial.home` 同一数据库语句的 `current_timestamp`（截到毫秒）作为时点。未来30天及当月损益共用它；余额读取最后一次维护刷新的物化结果；网络延迟和请求重试后的快照时点可能晚于点击/刷新时点。该时点返回前端并用于下钻，不能用客户端另取的时间替代。历史月份读取 balance_history 日终余额及显式期间损益、现金流。首页不显示逐笔交易；现金、余额、损益的逐日统计在对应报表面板，下钻链接带当天日期和对应科目/现金筛选。
